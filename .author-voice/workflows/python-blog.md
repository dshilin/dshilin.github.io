Результат внеси в ту же карточку статьи; отдельный конкурирующий контент-план не нужен. Если тема уже выбрана, проверь заполненную карточку без повторного общего опроса. Обычная корректура не требует нового стратегического разбора.

### Профессиональная цель — уточнение от 2026-10-28

Каждый технический материал должен помогать оценить Дмитрия как Python QA или Python-автоматизатора через конкретную задачу, личный вклад, проверку и границы результата. Источник поручения: `../examples/2026-10-28-python-positioning/review.md`. Цель не доказывает текущую квалификацию и не разрешает приписывать коммерческий опыт.

Перед выбором темы прочитай `.agents/product-marketing.md` (с учетом статуса черновика) и `.author-voice/python-content-map.md`. На основе фактической практики выбери один демонстрируемый навык. Заполни карточку из `.author-voice/templates/python-article-brief.md` в папке примера. Одна статья может показывать один навык; не нужно каждый раз перечислять весь стек и объявлять готовность к должности.

Для нового файла используй `hugo new content docs/python/YYYY-MM-DD-slug.md --kind python`. Шаблон устанавливает `draft: true`, `type: docs`, `career_track: python` и видимую пометку. Заполни `competencies` конкретным навыком, `description` — задачей и пользой разбора. Пустой список навыков означает незавершенную редакционную подготовку. Не публикуй незаполненный шаблон.

По уточнению Дмитрия от 2026-10-29 отдельные входы `/docs/` и `/docs/python/` исключены как дублирующие. Метаданные `career_track: python` включают статью в общий каталог `/blog/` при сборке, в которую входит сама статья; категории и темы дают тематические подборки. Каталог объединяет статьи из `docs/python` и `blog`, не копируя их. Структурные родительские файлы имеют `build.render: never` и `build.list: never` без каскада запрета публикации на дочерние статьи. Источник решения: `../examples/2026-10-29-python-page/review.md`. Существующий черновик про pytest остается по прежнему пути в `content/blog/`; будущие черновики создавай в `content/docs/python` по принятому правилу.

Техническая связка для читателя: проблема → решение → проверка → ограничения → профессиональное применение. Это ориентир для содержания, не обязательные одинаковые заголовки. Не дописывай рекламные обещания и недоказанную экономию времени. Личные статьи поддерживают общую миссию через реальные решения и подход к работе; для них не требуется искусственная вставка о Python.

### Подготовка текста

Готовь полноценный русскоязычный черновик технического поста по материалам текущего этапа обучения Python QA. Сохраняй результат отдельным Markdown-файлом в `C:/Users/user/Documents/Codex/dshilin.github.io/content/docs/python/YYYY-MM-DD-slug.md`.

Перед написанием прочитай `AGENTS.md`, `.author-voice/README.md`, `.author-voice/tone-of-voice.md` и релевантные примеры. Соблюдай правила архива: сохраняй версии и явную обратную связь отдельно от публикуемого контента. Подготовленный текст имеет статус «ожидает проверки», пока Дмитрий явно не подтвердит точную версию.

В YAML front matter каждого поста укажи `title`, `date`, `type: docs` и `draft: true`. В начале текста добавь видимую пометку «Черновик — ожидает авторской проверки». Не полагайся только на признак раздела: каждый пост должен иметь собственный `draft: true`.

Оформляй пост как связное объяснение: конкретная задача, небольшой пример входных данных, фрагменты кода с указанием языка, объяснение поведения, ожидаемый результат и практический вывод. Для темы тестирования добавляй показательные pytest-тесты, команды запуска и необходимые версии или зависимости. Различай ожидаемый вывод и фактически полученный: не утверждай, что код запускался, без подтверждённого запуска.

Используй доступные материалы занятий и подтверждённый прогресс. Не выдумывай личный опыт автора, выполненные задания, ошибки, результаты, commit или PR. Учебные примеры ассистента обозначай как учебные. Не раскрывай решение незавершённой самостоятельной диагностики; при недостатке материала выбирай независимый пример и явно указывай его происхождение. Технические утверждения сверяй с первичной документацией и давай ссылки.

Сохраняй существующие авторские правки. Следующий вариант уже подготовленного текста сохраняй отдельной версией по правилам архива. Не публикуй, не снимай `draft: true`, не выполняй commit или push без отдельного указания. В ответе укажи путь к черновику, тему и реально выполненные проверки.
